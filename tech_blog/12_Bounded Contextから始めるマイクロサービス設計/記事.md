# Bounded Contextから始めるマイクロサービス設計 - 分散した泥団子を避けるために

マイクロサービス設計で最も難しいことの一つは、「どこでサービスを分けるか」です。

小さく分ければよい、という話ではありません。
細かく分けすぎると、サービス間通信や分散トランザクションが増え、結果として「分散した巨大な泥団子」になります。

一方で、大きくしすぎると、変更容易性や独立デプロイ性が失われ、単なるモジュラーモノリス未満の構造になってしまいます。

では、どのように境界を考えればよいのでしょうか。

この記事では、次の2冊の内容を参考にしながら、自分なりにマイクロサービス設計の進め方を整理します。

* 『ソフトウェアアーキテクチャの基礎 第2版』
* 『ドメイン駆動設計をはじめよう』

中心になる考え方は、**Bounded Contextから始める**ことです。

つまり、いきなりサービスを切るのではなく、まずは業務上の文脈と言葉の境界を見つけ、その上でコンポーネントやサービス境界を継続的に見直していく、という進め方です。

## 全体の流れ

マイクロサービスの境界は、最初から一発で正解を出すものではありません。

最初に候補となるコンポーネントを作り、要件やユーザーストーリーを割り当て、責務を分析し、アーキテクチャ特性を考慮しながら、継続的に再構成していきます。

![](https://static.zenn.studio/user-upload/8e4cc89027e3-20260527.png)

出典：ソフトウェアアーキテクチャの基礎 8章

大まかな流れは次のようになります。

1. 核となるコンポーネントを識別する
2. コンポーネントにユーザーストーリーを割り当てる
3. 役割と責務を分析する
4. アーキテクチャ特性を分析する
5. 必要に応じて境界を再構成する

重要なのは、これは一方向の作業ではないということです。

一度コンポーネントを作って終わりではなく、要件の理解が進むたびに、境界を見直していく必要があります。

## 1. 核となるコンポーネントを識別する

最初に考えるべきことは、**だれが何をするのか**です。

ここで有効なのが、『ソフトウェアアーキテクチャの基礎』で紹介されている **アクター／アクションアプローチ** です。

### アクター／アクションアプローチとは

アクター／アクションアプローチとは、システムに関わるアクターと、そのアクターが行う主要なアクションから、候補コンポーネントを見つける方法です。

たとえば受注システムなら、次のように整理できます。

| アクター     | アクション                |
| -------- | -------------------- |
| 顧客       | 商品検索、注文、注文キャンセル、顧客登録 |
| オーダーパッカー | 箱サイズ選択、出荷準備完了の記録     |
| システム     | 在庫調整、支払い適用、補充発注      |

このように整理すると、単に「注文システム」と大きく捉えるのではなく、誰のためのどの操作なのかが見えやすくなります。

そして、それぞれのアクションに対応する候補コンポーネントを考えていきます。

たとえば、次のようなものです。

| アクション       | 候補コンポーネント             |
| ----------- | --------------------- |
| 注文する        | Order Placement       |
| 支払いを適用する    | Payment Processing    |
| 在庫を調整する     | Inventory Management  |
| 出荷準備完了を記録する | Order Fulfillment     |
| 注文状況を通知する   | Customer Notification |

この段階では、まだ厳密なサービス境界を決める必要はありません。

まずは、業務上の関心ごとを見つけることが目的です。

## 2. アクターが違うということは、ユビキタス言語が違うということ

アクターを分けて考える理由は、単に利用者の種類を整理するためだけではありません。

アクターが違うということは、見ている業務の文脈が違う可能性が高いからです。

そして文脈が違えば、同じ言葉でも意味が変わります。

### Bounded Contextとは

Bounded Context、つまり境界づけられたコンテキストとは、**あるモデルと言葉の意味が一貫して通用する範囲**です。

たとえば「見込み客」という言葉を考えます。

販売促進の文脈では、見込み客は「連絡先を伴う関心の通知」かもしれません。

一方で営業の文脈では、見込み客は「営業活動全体を管理する対象」かもしれません。

| 文脈   | 「見込み客」の意味     |
| ---- | ------------- |
| 販売促進 | 連絡先を伴う関心の通知   |
| 営業   | 営業活動全体を管理する対象 |

ここで重要なのは、組織全体で「見込み客」という言葉を無理に一つの意味に統一しないことです。

むしろ、文脈ごとに意味を明確に分けます。

文脈の内側で意味が一貫していればよい、というのがBounded Contextの考え方です。

## 3. Bounded Contextとマイクロサービス

マイクロサービスは、DDDのBounded Contextに強く影響を受けています。

各サービスは、自分のドメインで必要なモデル、ルール、データを内部に保持します。
そして、他のサービスとはコードやデータベースを安易に共有しません。

たとえば住所情報のような共通概念があるとします。

一見すると、住所を共通ライブラリとして切り出し、複数サービスから使いたくなります。
しかし、マイクロサービスではそれが必ずしも良い設計とは限りません。

配送文脈における住所と、請求文脈における住所では、必要な属性やバリデーションルールが異なるかもしれないからです。

その場合、無理に共通化すると、片方の文脈の変更がもう片方に影響します。

マイクロサービスでは、次の考え方が重要になります。

* 再利用は結合を生む
* 疎結合を優先するなら、共有より重複を受け入れる
* 各サービスは独立して変更・デプロイできるべきである

そのため、マイクロサービスは「何も共有しない」アーキテクチャとも呼ばれます。

もちろん、すべての重複を無条件に許容するという意味ではありません。
しかし、安易な共通化よりも、文脈ごとの独立性を優先する場面が多いということです。

## 4. アクターを元にBounded Contextを考える

Bounded Contextの適切な大きさは、最初から機械的に決められるものではありません。

重要なのは、先にモデルを理解し、その後で境界を決めることです。

単に「小さいサービスがよい」という考えで分割すると、後になって複数の文脈にまたがる変更が頻発します。
その結果、調整コストや技術的負債が増えてしまいます。

初期段階では、次の方針が有効です。

* 最初は広めのBounded Contextとして設計する
* 業務理解が進み、安定した境界が見えてから小さく分割する
* 中核領域と頻繁に連携する領域は、初期には同じ文脈に含めることも検討する

物理的に分離したサービスを後から統合するのは大変です。

一方で、論理的な境界を後から分割するほうが比較的容易です。

そのため、プロダクトの初期段階では、広めのBounded Contextから始めるのは現実的な選択だと思います。

特に、まだ業務理解が浅い段階でサービスを細かく切ると、境界の間違いがそのままネットワーク越しの依存関係として固定化されます。

最初は「将来分割できるように内部構造を意識したモノリス」や「広めのサービス境界」から始め、境界が見えてきたら分割する方が安全です。

## 5. マイクロサービス境界の上限と下限

DDDは、マイクロサービス境界を考えるための有効な手がかりになります。

特に重要なのは、次の二つです。

| DDDの概念          | マイクロサービス境界との関係 |
| --------------- | -------------- |
| Bounded Context | 有効な境界の最も広い側を示す |
| 集約              | 有効な境界の最も狭い側を示す |

![](https://static.zenn.studio/user-upload/2d16b203916b-20260527.png)

出典：ドメイン駆動設計をはじめよう 14章

Bounded Contextは、サービス境界の上限を考える助けになります。

それを超えて複数の文脈を一つに押し込めると、言葉の意味やモデルが混在し、大きな泥団子になりやすくなります。

一方で、集約はサービス境界の下限を考える助けになります。

集約よりも細かく分割してしまうと、本来一貫性を保つべき変更が複数サービスに分散します。
その結果、分散トランザクションや複雑な補償処理が必要になります。

つまり、サービス境界は大きすぎても小さすぎても問題があります。

| 境界                       | 問題         |
| ------------------------ | ---------- |
| Bounded Contextを超えて大きすぎる | 大きな泥団子になる  |
| 集約より小さく分けすぎる             | 分散した泥団子になる |

マイクロサービス設計で最も難しい問題の一つが、この境界の大きさです。

サービスを細かくしすぎると、処理のために大量のサービス間通信が必要になります。
逆に、大きくしすぎると独立性や変更容易性が失われます。

適切な境界を判断するには、次の観点が役に立ちます。

| 観点       | 判断基準                           |
| -------- | ------------------------------ |
| 目的       | 一つの重要な業務機能を提供しているか             |
| トランザクション | 同一トランザクションで強く協調する処理は同じ境界に置くべきか |
| 通信量      | サービス同士の通信が過剰になっていないか           |
| 変更単位     | 独立して変更・デプロイできるまとまりになっているか      |

特に重要なのは、トランザクションと通信量です。

サービス間で頻繁に同期通信が必要になる場合、その境界は細かすぎる可能性があります。
また、同じユースケースのために常に複数サービスを更新しなければならないなら、境界を見直すべきです。

## 6. コンポーネントにユーザーストーリーを割り当てる

候補コンポーネントを作ったら、次にユーザーストーリーや要件を割り当てます。

初期コンポーネントは、まだ空のバケツのようなものです。
そこにユーザーストーリーや要件を入れていくことで、具体的な役割と責務が見えてきます。

たとえば、次のように割り当てます。

| ユーザーストーリー / 要件 | コンポーネント               |
| -------------- | --------------------- |
| 注文を検証する        | Order Placement       |
| 箱のサイズを決定する     | Order Fulfillment     |
| 注文状況をメール通知する   | Customer Notification |
| 支払いを適用する       | Payment Processing    |
| 在庫を調整する        | Inventory Management  |

ここで重要なのは、どのコンポーネントにも自然に属さない要件に注目することです。

既存のコンポーネントに無理やり押し込むのではなく、新しいコンポーネントが必要なサインかもしれません。

たとえば、メール通知が複数のコンポーネントから使われる場合、それぞれに通知処理を重複実装するのではなく、Customer Notificationのような独立したコンポーネントとして切り出すことを検討できます。

ただし、ここでも安易な共通化には注意が必要です。

「複数箇所から使われるから共通化する」のではなく、そこに独立した責務や変更理由があるかを見ます。

通知のテンプレート、送信チャネル、再送、配信失敗時の扱いなどが独立して変わるなら、通知コンポーネントとして切り出す価値があります。

## 7. 分散トランザクションとサーガ

マイクロサービスでは、サービスをまたぐ単一のACIDトランザクションを構築することは避けるべきです。

これは、マイクロサービスの疎結合性と相反するからです。

基本原則は次の通りです。

> サービスをまたぐトランザクションが頻発するなら、まずサービス境界を見直す。

どうしても複数サービス間で一貫した処理が必要な場合には、サーガパターンを利用します。

サーガでは、各サービスが局所的なトランザクションを実行します。
途中で失敗した場合には、それまでの処理を取り消すための補償トランザクションを実行します。

たとえば注文処理では、次のような流れが考えられます。

1. 注文を作成する
2. 支払いを確保する
3. 在庫を引き当てる
4. 出荷を依頼する

途中で在庫引き当てに失敗した場合、支払い確保を取り消す必要があります。

これが補償トランザクションです。

ただし、サーガは便利な魔法ではありません。

実装、運用、監視、例外処理が複雑になります。
サーガが大量に必要になるなら、そもそもサービス境界が不適切な可能性があります。

マイクロサービスを設計するときは、サーガを前提にするのではなく、まずサーガを減らせる境界を探すべきです。

## 8. 役割と責務を分析する

コンポーネントに要件を割り当てたら、そのコンポーネントが責務を持ちすぎていないかを確認します。

ここで重要なのが凝集度です。

凝集度とは、コンポーネント内の操作や責務がどれだけ相互に関連しているかを表します。

たとえば、Order Placementに次の責務があるとします。

* 注文を検証する
* カートを表示する
* 配送先住所を決定する
* 支払い情報を収集する
* 注文IDを生成する
* 支払いを適用する
* 在庫を調整する
* 注文概要をメール送信する

これらはすべて「注文」に関係しています。

しかし、支払い、在庫、メール通知までOrder Placementに入れると、責務過多になります。

この場合は、次のように分けた方がよいかもしれません。

| コンポーネント               | 責務               |
| --------------------- | ---------------- |
| Order Placement       | 注文の作成、検証、注文IDの生成 |
| Payment Processing    | 支払い情報の処理、支払いの適用  |
| Inventory Management  | 在庫確認、在庫引き当て、在庫調整 |
| Customer Notification | 注文確認、ステータス変更通知   |

責務を分析するときには、コンポーネントの説明文を書いてみるとよいです。

たとえば、次のような説明になっていたら注意が必要です。

> Order Placementは、注文を検証し、支払いを処理し、在庫を調整し、さらに注文確認メールを送信する。

「および」「さらに」「また」のような接続詞が多くなる場合、そのコンポーネントは責務を持ちすぎている可能性があります。

コンポーネントは、なるべく一文で自然に説明できる責務に収めたいです。

## 9. アーキテクチャ特性を分析する

コンポーネント分割は、機能だけで決まるわけではありません。

スケーラビリティ、信頼性、可用性、耐障害性、弾力性、アジリティなどのアーキテクチャ特性も影響します。

たとえば、同じ「ユーザー入力を処理する」機能でも、次の二つでは求められる特性が異なります。

| 対象         | 求められる特性                |
| ---------- | ---------------------- |
| 一般ユーザー向け機能 | 高いスケーラビリティ、可用性、レスポンス性能 |
| 管理者向け機能    | 操作の正確性、監査性、保守性         |

数百人、数千人の同時ユーザーを扱う部分と、数人しか使わない管理者向け部分では、必要なスケーラビリティや可用性が異なります。

この場合、機能的には近く見えても、別コンポーネントに分ける判断が妥当になることがあります。

つまり、論理アーキテクチャを設計する前に、重要なアーキテクチャ特性を把握しておく必要があります。

特に、次のような問いを立てるとよいです。

* どの機能に高い可用性が必要か
* どの機能に高いスループットが必要か
* どの機能は障害時に縮退運転できるか
* どの機能は独立して頻繁に変更されるか
* どの機能は監査性や整合性が特に重要か

同じドメイン内に見える機能でも、求められるアーキテクチャ特性が大きく異なるなら、境界を分ける理由になります。

## 10. 最初から正しい境界を引こうとしない

ここまで見てきたように、マイクロサービス設計では、次のような観点を行き来しながら境界を考えます。

* アクター
* アクション
* ユビキタス言語
* Bounded Context
* 集約
* ユーザーストーリー
* 責務
* トランザクション
* 通信量
* アーキテクチャ特性

これらを一度に完璧に整理するのは難しいです。

そのため、最初から正しい境界を引こうとするよりも、境界を見直せる構造にしておくことが大切です。

特に初期段階では、次のような方針が現実的だと思います。

* 物理的なサービス分割を急がない
* まずは論理的な境界を明確にする
* Bounded Contextはやや広めに取る
* 集約より細かい分割は避ける
* サービス間トランザクションが頻発したら境界を見直す
* 業務理解が進んだら、安定した境界から分割する

マイクロサービスは、単にアプリケーションを小さく分ける技術ではありません。

独立して変更できる業務能力を、適切な境界で切り出す設計です。

そのためには、技術的な分割よりも先に、ドメインの分割を考える必要があります。

## まとめ

マイクロサービス設計では、いきなりサービスを切るのではなく、Bounded Contextから考えることが重要です。

アクターとアクションを整理し、ユビキタス言語の違いを見つけ、文脈ごとのモデルを明確にします。

そのうえで、ユーザーストーリーを候補コンポーネントに割り当て、責務や凝集度を分析し、アーキテクチャ特性も考慮しながら境界を調整していきます。

サービス境界には、広すぎる問題と細かすぎる問題があります。

Bounded Contextを超えて大きくしすぎると、大きな泥団子になります。
集約よりも小さく分けすぎると、分散した泥団子になります。

だからこそ、最初は広めのBounded Contextから始め、業務理解が進んだ段階で必要に応じて分割していくのがよいと考えています。

マイクロサービスの境界は、最初に決めるものではなく、ドメイン理解とともに育てていくものです。
